## النتائج التي تحتاج معالجة

### A-01 — P2: استهلاك حد تسجيل الدخول المشترك

**مثبت محليًا على نفس معالج Final باستخدام SQL الفعلي.** بعد 301 طلب بكود موظف غير صالح، أعاد طلب تسجيل دخول آخر 429. الحارس العام يعمل قبل التحقق من صيغة الكود، وحدّه 300 محاولة/5 دقائق لكل التطبيق، وليس لكل مستخدم. بذلك يمكن لمدخلات غير صالحة استهلاك الحصة المشتركة ومنع تسجيل الدخول مؤقتًا؛ الجلسات القائمة ليست ضمن هذا الاختبار.

الطلبات الـ301 نُفذت داخل العملية المحلية فقط، ولم تُرسل إلى Supabase. يثبت هذا سلوك التطبيق؛ قدرة ضوابط الحافة على منعه في الخدمة الحية لم تُختبر. الأولوية: التحقق من المدخلات قبل احتسابها، ثم مراجعة سياسة الحد لكل مصدر/حساب مع إبقاء الحماية العامة. يجب ألا يتحول الإصلاح إلى إزالة الحماية من التخمين.

### A-02 — P2: حد جسم الطلب يعتمد على Content-Length

**مثبت محليًا:** جسم JSON أكبر من 65,536 بايت، دون الهيدر، قُبل وأعاد 200. الهيدر المعلن الكبير يعاد له 413، لكن الحجم الفعلي لا يُقاس قبل req.json. هذا يضعف الحد على استهلاك الذاكرة/المعالجة. لا يثبت تعطل الخدمة أو عدم وجود حد أعلى على منصة الاستضافة. المطلوب قارئ محدود للحجم الفعلي، مع إلغاء القراءة وإعادة 413 عند التجاوز.

### A-03 — P2: JSON غير صالح يظهر كخطأ سيرفر

**مثبت محليًا:** JSON مقطوع يعاد له 500 بدل 400. لا ظهرت رسالة SQL أو stack trace في الرد المختبر، لكن التصنيف يشوش تنبيهات الأعطال وقد يسبب إعادة محاولة غير لازمة. المطلوب 400 واضح للـJSON غير الصالح مع الحفاظ على إخفاء أخطاء السيرفر الحقيقية.

### A-04 — متابعة أمنية للمكتبات

npm audit للإنتاج: صفر تنبيهات في اعتماديات حزمة Native، وثلاث حزم متأثرة في شجرة المخزن بدرجة moderate؛ ليست ثلاث ثغرات مستقلة. تنبيهان أصليان في yauzl وuuid، وExcelJS متأثر تبعيًا.

- `yauzl@3.2.0` مثبت أيضًا في deno.json للخدمة الحية. [GHSA-gmq8-994r-jv83](https://github.com/advisories/GHSA-gmq8-994r-jv83) يتعلق بمسار getLastModDate وملف ZIP ذي بيانات توقيت مشوهة. لم نجد استدعاءً لهذا المسار في كود الاستيراد الذي راجعناه، ولم نثبت استغلاله في التطبيق. يوجد إصلاح من 3.2.1؛ npm اقترح 3.4.0. يلزم تحديث مدروس واختبارات الرفع، دون npm audit fix عشوائي.
- [GHSA-w5hq-g745-h8pq](https://github.com/advisories/GHSA-w5hq-g745-h8pq) يتعلق بـuuid v3/v5/v6 عند تمرير buffer. استعمال ExcelJS الذي عُثر عليه هو v4؛ لم يثبت وصول مدخلات التطبيق للمسار المتأثر. اقتراح npm الرجوع إلى ExcelJS قديم ليس خطة إصلاح معتمدة.

## ما اجتاز الفحص

- الفني والمهندس لا يستطيعان تزوير Owner في جسم الطلب لتنفيذ 14 عملية إدارية لكل دور، ومنها اعتماد الإجازات والإضافي وتغيير المستخدمين وحذف البلاغ.
- SQL الجلسة الفعلي يرفض الجلسات المجهولة والمنتهية والملغاة بتغيير token_version والحساب المعطل. تغيير كلمة المرور الإجباري يمنع العمليات المحمية.
- Owner لا يستطيع تعطيل أو تخفيض صلاحية نفسه، ولا تغيير Owner آخر عبر محرر الموظفين. هذا فحص سلوك السيرفر، وليس تعديلًا لقائمة الأدوار في الواجهة.
- لا تمنح أدوار anon/authenticated امتيازات القراءة/الكتابة المباشرة لأي من 32 جدولًا داخل public وinv_lab وmaintrack_internal. جداول public لها RLS. غياب سياسات RLS هنا متوافق مع منع الوصول المباشر ومسار API الخاص؛ لم نفتح سياسات جديدة.
- دالة SECURITY DEFINER العامة الوحيدة التي ظهرت لا تقبل EXECUTE من هذين الدورين. مخطط inv_lab الخاص غير متاح لهما؛ غياب RLS عن بعض جداوله لا يعني أنها مكشوفة في الوضع الحالي.
- المصدر غير المسموح مرفوض، ردود API تحمل no-store وnosniff، ولم يظهر رمز الجلسة في الرد/السجل المختبر.
- المتصفح أثبت عدم إعادة تنزيل المخزن عند الرجوع، ومسح نسخة الحساب عند الخروج، ومنع أدوات Owner للفني، ورفض الرد المتأخر لإصدار قديم، والإلغاء وإعادة المحاولة، وCPU throttle ×4. البلاغات/التعديلات المعلقة تظل مانعًا للتفعيل.

## الأداء وحدود القياس

- بحث صناعي في 3,920 صنفًا، 30 بحثًا: p95 نحو **40.70ms**، والأقصى **82.60ms**. مخزن SQL مُحاكى، وليس زمن Supabase أو الشبكة.
- الرجوع الدافئ للمخزن في Chromium: **115ms** دون تنزيل snapshot إضافي.
- نسخة القرص الصناعية نحو 180,093 بايت. بعد عشر مرات رجوع زادت heap بعد GC بنحو 133,484 بايت؛ هذه لقطة واحدة، وليست إثبات انعدام تسريب ذاكرة طويل الأمد.
- سبعة طلبات حية خفيفة متتابعة فقط: health 200 (~5,145ms)، ready 200 (~1,742ms)، غياب الجلسة 401، مصدر مرفوض 403، مخزن دون جلسة 401، مسار قديم 410، الصفحة العامة 200 (~5,277ms).
- الأرقام الحية تشمل شبكة بيئة الفحص واحتمال البدء البارد، ولا تحدد سبب البطء أو p95 للمستخدمين. لم ننفذ ضغطًا على Supabase، ولا دخولًا بحساب حقيقي، ولا قياسًا على Oppo أو شبكة موظف.
- توجد CSP في meta للصفحة؛ لم يظهر CSP أو nosniff في HTTP response للصفحة العامة. تحسين رؤوس الاستضافة، بما فيه منع التضمين، يحتاج مراجعة إعدادات Vercel منفصلة. لا يثبت ذلك XSS قائمًا.
- مستشار Supabase أشار إلى سبع علاقات FK بلا فهرس تغطية وبعض الفهارس غير المستخدمة. لم نضف أو نحذف فهارس بناءً على التنبيه وحده؛ يلزم EXPLAIN وخطة نمو فعلية. pg_net في public تنبيه بنيوي أيضًا، دون إثبات استغلال هنا.

## الاستمرار والحدود

أُضيف اختبار Final الجديد وWorkflow منفصلان على فرع audit؛ الاختبارات الثلاثة الفاشلة تظل فاشلة بوضوح حتى الإصلاح. Workflow لا يملك أسرارًا أو خطوة نشر، ويثبت مصدر 0.4.10. ليس مراقبة مستمرة للنسخة الحية، وليس مدمجًا بعد في بوابة فرع الإصدار أو main.

التالي: إصلاح A-01 ثم A-02 وA-03 في تغيير محدود، إعادة نفس الاختبارات حتى تصبح خضراء، ومراجعة ترقيات المكتبات. بعد ذلك يمكن دمج البوابة في مسار الإصدارات وتشغيل مراقبة أخطاء/زمن استجابة فعلية. النسخة الاحتياطية الحديثة واختبار استرجاعها ما زالا معلقين على إجراء الكمبيوتر؛ هذه الاختبارات لا تعوضهما.

لم نعدّل مستخدمًا أو بلاغًا أو طلب إجازة/إضافي أو صنف مخزن، ولم نرسل بريدًا أو WhatsApp، ولم نغيّر سياسة أمان أو ننشر نسخة جديدة أثناء هذه المراجعة.
